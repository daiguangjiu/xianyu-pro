方案总览

本方案解决的核心问题：货品从入库到上架之间「检测—分级—贴标—建账」这一段，目前靠人工记在本子上，导致后续出库、报修、盘点、残值核算全部对不上账。系统把分级标准从「一张纸」变成「引擎里可执行的规则」。

要解决的 4 个痛点

  • 账实不符：货在手上，系统里查不到；或系统显示有货，人找不到
  • 分级靠嘴：不同检测员对同一台机器判定差一档，价差几百
  • 报修黑洞：机器寄出去了，没人跟进，钱垫着，货回不来
  • 报废即损失：D 档当废品扔掉，主板/电池残值白白流失

系统的 4 条铁律

  • 一码到底：条码终身不变，等级可变（字段而非换码）
  • 强制扫码：任何库存变动必须扫码，禁止直接改数量
  • 只认流水：库存余额由流水表算出，不允许直接改
  • 分级留痕：谁在何时判为哪档、改过几次、依据是什么，全留痕

交付形态建议

  • 扫码工作台（PWA）：检测员主力，手机/平板/电脑都能开，扫码即录
  • 管理后台（PC）：报表、盘点、对账、权限配置
  • 数据库：PostgreSQL + 对象存储（照片）
  • 离线优先：检测现场网络差时本地暂存，恢复后自动补传
  • 硬件接入：扫码枪（键盘模式）+ 标签机（网口 9100）→ 见 Tab 7，含实测结论
本章的硬件结论都已在本机实测：扫码检测算法通过 4 个场景验证（含噪声过滤）；标签打印三条链路的浏览器兼容性已确认；macOS 上标签机无官方驱动、不可用 CUPS 打标签——这是最容易踩的坑，详见 Tab 7 硬件接入。

1. 系统定位与边界

先说清「不做什么」——边界不清的系统最终都会变成大杂烩。

系统负责（范围内）

  • 批次/入库单管理，一机一码建档
  • 检测作业与记录留痕（含照片）
  • 分级判定与定价（规则可配置）
  • 标签打印与贴标复核
  • 库存台账（流水驱动）、仓位、盘点
  • 报修工单（线上/线下双通道）
  • 拆机件残值核算
  • 各类出库（销售/报修/调拨/拆机件）
  • 报表、权限、审计
  • 与中台/前参谋的数据同步

系统不做（范围外，靠对接）

  • 不做前台商城、交易、支付、客服 IM
  • 不做营销活动、优惠券、会员
  • 不做物流轨迹查询（对接快递鸟）
  • 不做财务总账、税务（对接财务系统）
  • 不做供应商门户（用 Excel 导入替代）
  • 不做图像 AI 自动判瑕（先留接口，二期再评估）
边界原则：本系统是「货品实体的状态与账本」，是库存真相来源（Single Source of Truth）。销售侧和财务侧的数据，本系统推送出去而非替代。

1.2 与分级标准的关系（复用而非重造）

分级标准是「业务规则」，本系统是「规则的执行引擎」。规则来自已确认的 5 档标准，映射关系如下。

等级业务定义系统状态默认仓位系统动作
S完美
零使用痕迹，电池≥85%可售 SELLABLE可售仓套系数 1.00，可直接上架
A微瑕
仅外观瑕疵，电池 80–84%可售 SELLABLE可售仓（微瑕区）套系数 0.85–0.92，强制填瑕疵描述
B小修
厂内可修，不必送官方待修 REPAIR维修仓生成维修工单，领料，修完复检重新定级
C报修
必须官方修报修在外 OUT_REPAIR报修仓（在外）生成报修工单（线上/线下），跟踪时效与费用
D报废
无维修价值或安全风险拆机件 PARTS / 危废 HAZARD拆机件仓 / 危废区强制逐件估值，残值入账
W 待测已建档未检测待检 PENDING待检仓仅内部可见，禁止上架/出库
状态与等级的映射关系要点：等级是永久属性（这台货永远是 B），状态是当前处境（B 修好后变成 S 并进入可售）。所以字段要分开存：grade（等级，只由检测决定）与 status（状态，由作业流转决定）。混在一起是这类系统最常见的设计错误——会导致「B 档待修」和「B 档可售」无法区分。

2.2 五类异常分支

E1检测存疑（判「?」）
  • 自动进入复检池，状态仍 PENDING
  • 指派资深检测员复检，不隔夜（系统标记超时）
  • 复检结论覆盖建议档位，两次记录都留痕
E2检测中发现安全红线
  • 鼓包/漏液/异味/漏电/焦糊/火烧痕迹
  • 状态直接置 危废 HAZARD，禁止充电与任何流转
  • 强制拍照 + 危废台账 + 单独仓位
E3贴标后复核不通过
  • 扫码读出等级 ≠ 系统等级 → 阻断入库
  • 生成补打任务，记录补打原因与次数
  • 同批标签错贴超阈值 → 告警升级主管
E4报修超时未回
  • 按承诺时效倒计时，默认 15 天预警
  • 超时进「待处理」列表：联系客服撤单 / 转 D 拆件
  • 撤单后机器回仓需重新检测定级（可能降档）
E5盘点差异
  • 生成差异单，不允许直接改库存
  • 需审批 → 生成盘盈/盘亏调整流水
  • 差异率超阈值（如 >0.5%）自动升级主管核查

3. 分级标准（业务口径全文）

这一章是检测员判定作业的唯一依据，也是 Tab 11 分级引擎规则表的数据来源。建议打印上墙。

3.1 五档分级总表（检测员判定依据）

档判定条件（全部满足）处置动作定价
S
 ① 全部功能正常无异常
② 零使用痕迹：屏幕无划痕、机身无磕碰、无掉漆、边框无磨损
③ 电池健康 ≥ 85%
④ 无拆修、无进水、无换屏
⑤ 配件齐全、附件无损		 拍实物图 → 定基准价 → 上架 系数 1.00
A
 ① 功能全好，仅外观问题
② 允许：细微划痕（屏面划痕 ≤ 2 条且不影响显示）、边框/后盖轻微磕碰掉漆、按键轻微磨损
③ 电池健康 80%–84%

② 主板完好、无进水、无烧痕
③ 修完可恢复 S/A 状态

 ① 故障超出厂内能力或官方要求原厂件/授权认证
② 修后价值 > 修复成本 × 1.5（值得修）

 命中任一即报废（不再评估维修）：

② 屏总成报废且官方换屏报价 > 整机价 × 60%
③ 主板烧毁 / 进水腐蚀 / 无信号无供电，修后价值 < 成本
④ 火烧 / 进液 / 严重变形（结构性损伤）
⑤ 无法正常开机且无维修价值
⑥ 缺主板/缺屏/缺电池等主要部件，按拆件处理

判定优先级：安全 > 核心功能 > 次要功能 > 外观。任一项触发更高等级，按最高等级归类（就高不就低）。
例：外观全新但屏碎 → C 报修，不是 A 微瑕。例：功能全好但电池鼓包 → D 报废，不是 C。
⚠ D 档不是「废品」：玻璃碎屏、缺主板的机器，主板/摄像头/电池/屏总成仍值整机 30–60%。必须建档、贴标、单独入库为「拆机件」，否则等于把已付费的货当废品扔掉——这是本批货最大的一块隐性损失。详见 Tab 6 库存口径。

3.8 抽检与质量控制

抽检机制

  • 每定级 50 台，资深检测员随机抽 10% 复检
  • 重点抽：高价值（>¥3000）、S 档（虚报高发）、D 档（怕被误报废）
  • 连续 3 次误判 → 停线重训
  • 存疑判「?」→ 自动进复检池，不隔夜，当天复检

三项质量指标（进管理看板）

  • 误判率 = 复检不一致台数 / 抽检台数（目标 < 3%）
  • 漏检率 = 售后返修台数 / 已售台数（目标 < 1.5%）
  • 引擎一致率 = 建议档=最终档台数 / 总台数（低则规则需调）
⚠ S 档是虚报重灾区：「零使用痕迹」是主观判断，检测员为了好卖容易放宽。必须靠侧光验屏 + 显微镜看划痕 + 拍照留证三件事硬约束，否则 A 档当 S 档卖，纠纷和退货成本远超那点价差。

3.9 五种最易踩的损耗（务必逐条核对）

① 把 D 档当废品扔了

整机判废前必须逐件估值。一台屏碎主板好的手机，主板能值整机 40%。本批货若有 200 台判 D，按残值 30% 算就是几万块——这是最大一块隐性损失。

② 标签贴错 / 贴反

等级色块是分拣指令，贴错会导致高价机当微瑕卖（少赚）或低价值当完美卖（退货+差评）。贴标必须扫码复核，不匹配直接阻断（见 3.11 与 Tab 9 硬件接入）。

③ 报告修但没跟进

C 档发出后必须建「待修台账」：凭证号、承诺时效、费用、状态。超过 15 天未回直接联系客服撤单或转 D，否则货压在别人手里，钱也垫着。

④ 账号锁 / 数据没清

二手流通最典型的纠纷：买家登录你的账号。原机主账号未解绑 → 只能判 D。检测时必做「设置-账号-退出全部账号 + 恢复出厂」并录像。

⑤ 小家电异味未除

清洁消毒必做，这是转卖投诉重灾区。上一批机器若有异味，下一批买家投诉会连带影响店铺信誉。

⑥ 报修白跑一趟

线下送修前务必先电话确认网点是否受理该机型/该故障，避免机器白带、路费白花、时间白耗。

4. 库存模型（账实一致的核心设计）

二手货的特殊性：同一台货会在多个状态间来回移动（待检→可售→锁定→销售，修不好还要退回）。如果用「数量字段直接加减」，必然对不上。

4.1 三个必备原则

① 余额由流水算出

库存数量 = SUM(流水). 数据库层面禁止直接 UPDATE items.stock 字段，用触发器抛异常或撤销 UPDATE 权限。这样任何库存变动都有据可查。

② 强制扫码，禁改数量

所有出库/入库/移库都要求扫条码。没有条码的操作一律拒绝，防止「一错百错」——错一个数量，整批账都歪。

③ 在途库存单独计

报修寄出的货物理上不在你手上，但钱已垫付。必须单列 in_transit 口径，不能算在「可售」里。

-- 库存余额表（由流水汇总，写入时校验） stock_balance(item_id, warehouse_code, status, qty, in_transit_qty, last_ledger_id, updated_at) -- 库存流水表（只增不改，append-only） stock_ledger( id, item_id, -- 货品 biz_type, -- INBOUND/GRADE/LABEL/UP/MOVE/OUT/LOCK/UNLOCK/SCRAP/ADJUST biz_id, -- 关联单据 from_warehouse, to_warehouse, from_status, to_status, qty_delta, -- 数量变化（通常 ±1） operator_id, operated_at, remark, -- 必填场景：补打/盘盈/盘亏/报废 _idempotent_key -- 幂等键，防重复提交 )

6. 功能模块详细设计

按开发优先级排序。每个模块给「核心能力 / 关键设计 / 验收标准」。

1批次与建档P0 · 库存起点

核心能力

  • 建批次单：来源类型、供应商、品类、预计数量、批次号
  • 号段预留：系统分配 YYMM-NN-0001~9999，全批不重号
  • 两种入库模式：一机一码（每台生成唯一码）/ 按型号批量（同型号多台，仅序列号不同）
  • 入库即拍照，作为后续争议凭证

关键设计

  • 条码生成必须服务端，客户端不参与（防重号）
  • 号段用数据库序列或行锁分配，禁止并发下重复发号
  • 批量模式支持 Excel 导入序列号，导入时校验格式与重复
验收标准：① 100 台同批建档零重号；② 并发 10 路同时建档不重号；③ 批量导入 1000 条错误能在 3 秒内定位到具体行
2扫码检测工作台P0 · 最高频

核心能力（检测员一天用 6 小时的主界面）

  • 扫码即载入：扫 W 占位码 → 自动带出品类、品牌型号、批次、历史检测记录
  • 一屏完成：11 个检测项下拉（√/×/不适用）+ 电池% + 不合格描述 + 建议档位实时刷新
  • 档位建议引擎：按规则实时算建议档位与依据（如「电池 78% 低于 A 档阈值 80% → 建议 B」）
  • 离线可用：断网时本地暂存，网络恢复自动补传
  • 防错：不合格项未填描述不允许提交；命中安全红线立即弹危废流程
  • 音效 + 色块反馈，检测员可盲操作

关键设计

  • 为 PWA，支持扫码枪（USB 键盘模式）与摄像头扫码
  • 检测项按品类动态渲染（手机/笔记本/家电检项不同）
  • 连续录入不刷新页面，焦点自动跳下一台，不打断节奏
  • 「?」存疑一键标记，自动进复检池
验收标准：① 熟练工 ≥40 台/人/天；② 断网检测 20 台后恢复，数据 100% 补传无丢失；③ 不合格项未填描述无法提交；④ 扫码到载入档案 < 300ms
3分级与定价引擎P0 · 规则可配置

核心能力

  • 分级规则配置化：管理员在后台改规则，不改代码，即时生效

  • 定价：基准价 × 系数 → 销售价；低于底价自动拦截需审批
  • 毛利率校验：售价低于成本 × (1+最低毛利率) 时警告

7.1 扫码枪接入（键盘楔形模式 · 零成本）

扫码枪本质是「高速键盘」：扫一次码 = 极快地敲一串字符 + 自动回车。不用驱动、不用 SDK，一个键盘事件监听就搞定。

核心原理：用时间间隔区分「扫码」与「手打」

来源相邻字符间隔结束符特征
扫码枪5–20ms自动回车极快、连续、不可中断
人工打字≥ 80ms手动回车慢、有停顿、可能有退格
粘贴无（一次性）手动首字符即完整串，间隔为 0
// ✅ 已实测通过 4 个场景的检测器（可直接抄进项目） class ScannerDetector { constructor(opts = {}) { this.maxGap = opts.maxGap ?? 45; // 扫码相邻字符最大间隔(ms) this.minLen = opts.minLen ?? 8; // 最短条码长度，过滤误触 this.onScan = opts.onScan; this.buf = ''; this.last = 0; this.firing = false; } handle(e) { const k = e.key; // 结束符：回车 / Tab if (k === 'Enter' || k === 'Tab') { if (this.firing && this.buf.length >= this.minLen) this.onScan(this.buf); this.reset(); e.preventDefault(); return; } if (k.length !== 1) return; // 忽略控制键 const now = e.timeStamp || performance.now(); // 间隔超时 → 判定为人工输入，清空重来 if (this.firing && now - this.last > this.maxGap) { this.firing = false; this.buf = ''; } if (!this.firing) { this.firing = true; this.buf = ''; } this.buf += k; this.last = now; } reset() { this.firing = false; this.buf = ''; } start(target = document) { this._h = e => this.handle(e); target.addEventListener('keydown', this._h, true); // 捕获阶段，能抢在输入框之前 } stop(target = document) { target.removeEventListener('keydown', this._h, true); } } // 用法：全局挂载，检测员无需对准任何输入框，扫即触发 const scanner = new ScannerDetector({ onScan: code => onBarcodeScanned(code) }); scanner.start();
实测验证结果（4 场景全通过）：
① 扫码枪 8ms 间隔 13 位 → ✅ 正确识别 QCPHS26100012
② 人工打字 150ms 间隔 → ✅ 正确忽略（不误判为扫码）
③ 先误按 1 个噪声键再扫 → ✅ 噪声被超时重置丢弃，不产生脏数据
④ 边界 38ms 慢速扫码 → ✅ 正常识别（说明 45ms 阈值留了余量，合理）
为什么用 e.timeStamp 而不是 Date.now()：前者是事件硬件时间戳，不受主线程繁忙导致的 JS 执行延迟影响。检测高峰期（连续扫几十台）时 Date.now() 可能因为渲染阻塞而误判为人工输入，timeStamp 不会。

检测员工作台的扫码交互（关键：不用鼠标）

环节行为设计为什么这样
① 扫码扫 W 占位码 → 自动载入该货品档案（品类/型号/批次/历史）检测员不用手填任何东西
② 录入11 个检测项用单键热键：按 1=合格、2=不合格、3=不适用，空格=下一项双手不离开键盘，节奏不被打断
③ 提交按 Enter 提交，自动清空并聚焦下一台连续作业不被打断
④ 反馈绿/黄/橙/红整屏色块 + 音效（可关）余光即可确认等级，不需读字
⑤ 存疑? 键标存疑 → 自动进复检池拿不准的不硬判
⚠ 必做的两个防误操作：① preventDefault() 必须开，否则扫码末尾的回车会误触发表单提交或跳到下一个输入框；② 输入框要设 readonly 或 disabled，强制所有数据来自扫码，杜绝手打混入脏数据。

7.4 TSPL 标签指令（国内标签机通用，已校验）

国内主流标签机（芯烨/佳博/汉印/TSC）大多兼容 TSPL 指令集。直接发指令即可打印，不用 SDK。

SIZE 60 mm, 40 mm ← 标签物理尺寸（必须与实际标签一致） GAP 2 mm, 0 mm ← 间隙高度与偏移 DIRECTION 1 ← 打印方向 CLS ← 清空打印缓冲区（必须在内容之前） TEXT x,y,"字号",粗细,倍数,"内容" TEXT 15,30,"3",0,1,1,"S" ← 等级大字 TEXT 80,30,"2",0,1,1,"手机" ← 品类 TEXT 15,48,"1",0,1,1,"QC-PH-S-2610-0012" ← 人可读编码 BARCODE x,y,"码制",模块宽,高,方向,校验,比例,"内容" BARCODE 15,52,"128",42,1,0,2,2,"QCPHS26100012" ← 核心：条码 PRINT 1,1 ← 打印并走纸 1 份（必放最后）
已校验：① 指令齐全 SIZE/GAP/CLS/BARCODE/PRINT；② 顺序正确（CLS 在 PRINT 之前）；③ 我们的条码 QCPHS26100012 编码后 178 模块，按 0.19mm/模块约 33.8mm，远小于 60mm 标签宽度，条码可扫。
注意：TSPL 的 BARCODE 由打印机自己生成 Code128，不需要我们传模块串——直接把明文传进去即可，比自绘 SVG 更可靠（打印机有专门的条码合成电路）。
ZPL（斑马系）指令对照：^XA ... ^XZ 包裹整个标签，条码用 ^FO x,y ^BY w,h ^BCN,高,校验,行 ^FD 条码 ^FS。如果买的是斑马或兼容 ZPL 的机型，指令换一套即可，业务逻辑完全不变——所以建议做一层打印指令适配器（见 7.5）。

复核的 3 项强校验

扫到新码后，后端校验： ① 新码解析出的 barcode 是否存在 否则「未知条码，拒收」 ② 新码等级 == 该货品当前系统等级 否则「等级不符：系统=S，实扫=A，拒收」 ③ 新码 barcode == 该货品原 barcode 否则「张冠李戴，检查是否贴错机器」 全部通过 → status 置 GRADED/SELLABLE，移入对应仓 → 打印记录落库
操作建议：不要撕掉 W 占位标。在 W 标上划一道横线作废即可。理由：① 撕标签容易连机器边缘的旧胶一起扯下来；② 保留痕迹便于事后追溯这批货的流转过程；③ 减少一次操作就减少一次出错机会。
⚠ 补打要受控：标签损坏/丢失需要补打时，必须填原因并记录到 label_print_log。同批补打率 > 1% 说明前面流程有问题，要告警排查，别让补打变成常态。
为什么标签机不能省：前面提过——面单打单纸粘性差、防水差、字会褪。货品身份码要跟着机器流转两三年，必须用不干胶。而且正式码上的等级色块是分拣指令，仓管不用看字就知道这批货该去哪个架。

7.2 报修出库与回库（最容易失控的环节）

  • 序列号 / IMEI（官方无凭证不受理）
  • 购买凭证截图（有订单号优先）
  • C1：京东/400 工单号、寄修单号
  • C2：网点名称、电话、地址、受理确认记录
  • 承诺时效（默认 15 天，可按品牌调整）
  • 预估费用（超成本阈值需审批）

  • 状态 OUT_REPAIR → 强制重新检测，不可直接回可售
  • 重新定级（可能降档，维修可能引入新伤）
  • 重新定价（原售价不再沿用）
  • 费用核销：官方报价 vs 垫付金额 vs 最终残值
  • 若官方判定不可修 → 转 D 拆件，凭证截图存档
  • 若撤单回仓 → 重新入检测流程
超时机制（务必配定时任务）：① 接近承诺时效（如剩 3 天）提醒；② 超过承诺时效标 timeout_flag=true 并进「待处理」列表；③ 主管可一键「联系客服撤单」或「转 D 拆件」，全部留痕。
真实教训：不建待修台账，货寄出去就等于丢了——钱垫着、货在别人手里、没人跟进。

8. 分级引擎（规则如何真正跑起来）

分级不是写死在代码里的 if-else，而是存在数据库里的配置。这样业务口径变化（电池阈值从 85% 调到 82%）不需要改代码发版。

8.1 规则数据结构

dict_grade_rule ├─ id, priority 优先级（小数字先匹配） ├─ category 适用品类（PH/TB/NB/...，* = 通用） ├─ conditions (jsonb) 条件表达式，见下 ├─ grade 命中后判定的等级 S/A/B/C/D ├─ safety_flag 是否为安全红线规则（true 时直接判 D） ├─ effective_from / to 生效期（换标准不丢历史） └─ enabled 启停开关 -- conditions 示例 {"all_of":[ {"field":"battery_health","op":">=","value":85}, {"field":"all_items_pass","op":"==","value":true}, {"field":"flaw_count","op":"==","value":0} ]} {"any_of":[ {"field":"safety_hit","op":"==","value":true} ],"safety_flag":true,"grade":"D"}
为什么要保留生效期：今天定 S 的货，按旧标准存；下月标准改成 90%，历史货不该被追溯重判。test_record 里要快照当时命中的规则 ID，保证可复现。

8.4 抽检与质量控制

抽检机制

  • 每定级 50 台，资深检测员随机抽 10% 复检
  • 重点抽：高价值（>¥3000）、S 档（虚报高发）、D 档（怕被误报废）
  • 连续 3 次误判 → 停线重训

三项质量指标（进管理看板）

  • 误判率 = 复检不一致台数 / 抽检台数（目标 < 3%）
  • 漏检率 = 售后返修台数 / 已售台数（目标 < 1.5%）
  • 引擎一致率 = 建议档=最终档台数 / 总台数（低则规则需调）
S 档是虚报重灾区：「零使用痕迹」是主观判断，检测员为了好卖容易放宽。必须靠侧光验屏 + 显微镜看划痕 + 拍照留证三件事硬约束，否则 A 档当 S 档卖，纠纷和退货成本远超那点价差。

部署Docker Compose 或托管 PostgreSQL数据是命脉，必须有备份和恢复演练云托管（Vercel + Supabase/Neon）
选型的关键约束是「扫码必须能打」：标签打印优先走 网口 RAW 9100 直连（见 Tab 7），不要设计成「点打印 → 请求服务端 → 服务端连打印机」的串行强依赖。必须内置断网兜底（浏览器直连），否则网络波动时检测员无法贴标，整条流程立刻卡住。
特别注意：macOS 上标签机基本没有官方驱动，切勿用 CUPS 通用驱动打标签（尺寸每次复位、条码模糊不可扫）。CUPS 只用于打 A4 检测单。

11.3 数据安全与备份（不可省）

  • 每日全量 + 实时 WAL 归档，异地保留 ≥30 天
  • 每季度恢复演练——没演练过的备份等于没有备份
  • 敏感字段（客户信息、序列号）加密存储
  • 操作日志与库存流水只增不改，防篡改
  • 照片单独存对象存储，DB 只存 URL
  • 高价值操作（改价/报废/撤单）二次确认 + 审批
  • 账号强制密码策略，禁用共享账号
  • 内网访问 + VPN，禁止公网直连数据库

11.5 与既有分级标准文档的关系

本方案的 5 档分级、报修分流、拆机件残值口径，完全沿用《二手货品检测分级标准 V1.0》，未做任何改动。两者关系：

分级标准文档（业务侧）

  • 给检测员看的作业手册
  • 判定条件、B/C 档清单、报修路径
  • 可打印上墙、纸质留存

管理系统（本方案，系统侧）

  • 把标准变成可执行规则并自动计算
  • 标准变更时改配置，不改代码
  • 标准里的每条判定都有数据留痕与执行统计
标准与系统必须同源：建议把分级标准文档的判定条件，直接转成 dict_grade_rule 表的初始数据（脚本导入），保证纸质标准与系统规则完全一致。以后改标准，两边同步改，避免出现「纸上写 85%、系统判 82%」的混乱。
