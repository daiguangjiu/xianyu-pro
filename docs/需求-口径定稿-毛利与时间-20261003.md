## 一、毛利口径（定稿）

### 1.1 公式

**平台端（渔枢系统，`orders` 表）**
```
毛利 = 销售价 − 运费 + 退款给客户 − 成本价 + 供应商退款 − 平台技术服务费
```

**渔货栈（渔货栈，`downstream_orders` 页面展示）**
```
毛利 = 销售价 − 运费 + 退款给客户 − 渔货价 + 平台退款 − 平台技术服务费
```

两个公式**同构**：渔货栈的上游就是平台，所以把平台端的「成本价 + 供应商退款」换成渔货栈的「渔货价 + 平台退款」即可。
**运费固定减在销售价之后**（拍板 2026-10-03），公式顺序即代码顺序，方便一眼核对。

### 1.2 每一项取哪一列

| 项 | 平台端（渔枢系统） | 渔货栈 | 说明 |
|---|---|---|---|
| 销售价 | `deal_amount ?: sale_amount` | 同（经 `hub_orders` 透传的 `paid`） | 买家实付，有成交价取成交价 |
| **运费** | `shipping_fee` | 同（透传） | **减在销售价之后**（拍板） |
| **成本价** | `cost_amount` | — | **自营飞书群同步的成本价**，页面文案标注为「成本价（飞书群同步）」 |
| **渔货价** | — | `supplier_items` 渔货价（`fish_price` / `cost_price`） | 渔货栈向平台采购的价＝渔货栈的成本价 |
| 退款给客户 | `refund_amount`（**负值**） | 同 | 钱出去 |
| 供应商退款 / 平台退款 | `supplier_refund_amount`（**正值**） | 平台端同名列的镜像 | 钱进来；在渔货栈叫「平台退款」 |
| 平台技术服务费 | `platform_fee` | 同（透传） | 0.6%（店铺可单独设费率） |

非退单订单两个退款字段都是 0，公式自动退化成「销售价 − 运费 − 成本价 − 平台技术服务费」，不需要特判。

### 1.3 运费口径（已定稿 2026-10-03）

**运费计入毛利，且紧跟销售价之后扣减**：

```
毛利 = 销售价 − 运费 + 退款给客户 − 成本价 + 供应商退款 − 平台技术服务费
```

- 与当前实现一致（`app/models.py:411-427` 的 `net_profit`、`app/services/finance.py:86` 的应付 `payable = cost + shipping` 都含运费）→ **历史毛利数字不跳变**，本次只是把退款两项补进公式；
- 资金页「预计毛利」、看板毛利统计、订单详情、渔货栈订单详情**四处同一个数**，都以 `finance.order_amounts` 为唯一实现。

### 1.4 金额符号口径（定稿）

- **给出去的钱存负**：`refund_amount`（退款给客户）
- **收回来的钱存正**：`supplier_refund_amount`（供应商退款 / 平台退款）
- **结算流水 `settlements.amount` 仍存正数**，方向由 `direction=out/in` 表达 → 生成退款流水时取 `abs(refund_amount)`
- **页面展示保留符号语义**：「退款给客户 −¥50.00」「供应商退款 +¥30.00」
- **例外**：`daily_summary_logs.refund_amount`（每日汇总的「退单金额合计」）建议保持正数合计并注明是汇总值，别让符号口径污染统计

## 二、时间口径（定稿）

### 2.1 先回答你的问题：服务器时区是北京时间吗？—— **是**

```
Dockerfile:5         ENV ... TZ=Asia/Shanghai
Dockerfile:19-20     ln -snf /usr/share/zoneinfo/$TZ /etc/localtime && echo $TZ > /etc/timezone
docker-compose.yml:12/34   TZ: Asia/Shanghai
```

所以 `datetime.now()`（本地 naive）本身就是北京时间，跟 `app.timeutil.now()` 一个值。
**真正有问题的是显式写 `datetime.now(timezone.utc)` 的那 20+ 处** —— 它存进去的是 UTC 时刻，页面按北京时间渲染，显示出来比真实时间早 8 小时（`src/web/router.py:318/491/661`、`src/goods/service.py:44`、`src/goods/sync.py:298`、`src/merchant/service.py` 8 处、`src/channel_xianyu/*`、`src/logistics/service.py:51`）。

### 2.2 定稿

1. **存储 = UTC**
2. **传输 = ISO8601**（`2026-10-03T06:23:00Z` 或带 `+08:00` 偏移）
3. **展示 = 按用户时区**（默认 `Asia/Shanghai`，可取浏览器时区 / 账号设置）

### 2.3 改造步骤

| 步 | 内容 | 位置 |
|---|---|---|
| 1 | 写入侧统一 `app.timeutil.utc_now()`（**已存在**：`app/timeutil.py:24`） | 替换 `src/` 里全部 `datetime.now(timezone.utc)` 与 `datetime.now()`（含 `src/order/state.py:243`、`src/goods/service.py:49/72`） |
| 2 | 存量迁移：新增 `app/db.py::_migrate_utc_time()`（参照现有 `_migrate_beijing_time()`，**反向 −8h**），启动时跑一次、幂等 | `app/db.py:119/183` |
| 3 | 传输：新增 `to_iso(value)`；API/JSON 里的 datetime 一律 ISO8601 | 新增工具函数 + 各 JSON 出口 |
| 4 | 展示：新增模板 filter `\| dt`（按用户时区格式化），替换模板里散落的 `x.strftime('%Y-%m-%d %H:%M')` | `app/templates/*`、`templates/*` |
| 5 | 用户时区来源：首次访问由 JS 写 `tz` cookie（`Intl.DateTimeFormat().resolvedOptions().timeZone`，兜底 `Asia/Shanghai`），服务端按它渲染；前端对带 `data-ts="<ISO8601>"` 的 `<time>` 元素再按本地时区精修一次 | `templates/base.html` + `app/static/app.js` |
| 6 | 输入侧：表单 `datetime-local`（如商品「最近上架」`products.listed_at`）按用户时区解释后转 UTC 存 | `app/web/pages.py` 相关 POST |

### 2.4 存储格式：**naive UTC**（已定稿 2026-10-03）

库里所有 datetime 列存 **UTC 的 naive 值**（不带 tzinfo）：

- 现有 `DateTime` 列**一列都不用改**（SQLite 本来就不存时区信息），改动面最小；
- 靠两条全局约定守住：① 写入一律 `app.timeutil.utc_now()`；② 静态断言用例禁止业务代码出现 `datetime.now()` / `datetime.now(timezone.utc)`；
- 不采用 aware UTC —— SQLite 会把带偏移的 datetime 存成字符串，现有比较 / 排序 / 区间筛选（按天下单、账单日、超时扫描）要全部重查，风险大。

### 2.5 存量数据：**一次性迁移**（已定稿 2026-10-03）

- 启动时跑一次 `app/db.py::_migrate_utc_time()`（参照现有 `_migrate_beijing_time()`，**反向 −8h**），带幂等标记，重复启动不会再跑；
- 迁移后页面显示时间**与迁移前完全一致**（存 −8h、渲染按 `Asia/Shanghai` +8h 回来），用户无感；
- 迁移前先自动备份 SQLite 文件，失败可回退。

### 2.6 验收

- 静态断言用例：业务代码（除 `app/timeutil.py`）不得出现 `datetime.now(timezone.utc)` / `datetime.now()`；
- 造一单：库里存 UTC，页面按 `Asia/Shanghai` 显示；把 `tz` cookie 改成 `UTC` 后显示跟着变 8 小时；
- 迁移后抽查 10 条订单：页面显示时间与迁移前**完全一致**（存 −8h、渲染 +8h）。

## 七、第二批落地情况：时间口径（2026-10-03 已实施）

定稿口径：**存储＝UTC naive，传输＝ISO8601，展示＝按用户时区（默认北京）**。

| 步 | 内容 | 落地 |
|---|---|---|
| 1 | 写入统一 UTC | `app/timeutil.py` 提供 `now()` / `utc_now()` / `beijing_now()`；`src/` 里最后 3 处裸 `datetime.now()` 清掉（`src/order/state.py::_now` → `utc_now`，商品编号 / 商家编码日期 → `beijing_now`）；新增静态断言用例守着 |
| 2 | 存量迁移 | `app/db.py::_migrate_utc_time()`（渔枢系统表整表 −8h + 渔货栈 `channel_listings` / `stock_orders` / `shop_goods` 指定列），幂等标记 `2026-10-utc-time`，迁移前备份 |
| 3 | 传输 | `timeutil.to_iso()`（默认出 `...Z`，给时区出偏移） |
| 4 | 展示 | 两端模板统一 `\| dt` 过滤器（`app/web/pages.py`、`src/web/router.py` 各注册一份），模板里零 `strftime` |
| 5 | 用户时区 | `templates/base.html`（两端）首访写 `tz` cookie；`app/main.py::TimezoneMiddleware` 按 `?tz=` / cookie 写进 `timeutil.current_tz`；`human_time()`、`timeutil.fmt()` 默认读它（脱离请求按北京） |
